# AGENTS.md

This file provides guidance to Codex when working with code in this repository.

## Commands

```bash
pip install -r requirements.txt   # install deps
python -m unittest -v             # run the self-check (test_app.py)
python app.py                     # run the Flask backend locally (port from $PORT, default 8787)
python register_commands.py       # (re)register the /抓圖 slash command — only needed when the command's options/shape change
```

Deploy: push to `main` on GitHub → Render auto-deploys (Build: `pip install -r requirements.txt`, Start: `waitress-serve --host=0.0.0.0 --port=$PORT app:app`). No CI; the unittest run above is the only check before pushing.

For instant (non-1-hour-propagation) slash-command testing, set `GUILD_ID` in `.env` before running `register_commands.py`, then unset it and rerun before shipping (global commands only, so anyone who installs the app can use it).

## Architecture

This bot does **not** search X/Instagram/Facebook live. `/抓圖 <角色> <類型>` just returns a random pick from `collected.json`, a personal collection built entirely by a browser userscript reacting to the user's own likes. There is no scraping and no official-API integration — see the README's "為什麼是「按讚蒐集」" section for why that was deliberately ruled out (paid-only official API, unsafe third-party scrapers, and a firm decision not to build anti-bot-bypass tooling even for a personal project).

Three curation commands sit alongside `/抓圖`, registered by the same `register_commands.py`: `/抓圖清單 <角色> [類型]` shows counts (`build_list_content` in app.py) plus up to 15 entries as clickable links (newest-added first — see the `added_at`/ordering note below), since there was previously no way to see what had actually been collected; `/抓圖刪除 <角色> <網址>` removes one entry by URL match (`delete_entry`), with the `網址` field itself autocompleting against that character's own collected entries (`url_choices`, filtered by author or URL substring) so there's no need to run `/抓圖清單` first just to copy a link; `/抓圖統計 [角色]` shows aggregate counts across every character plus a top-10 list (`build_stats_content`) — the `角色` option is optional and additive: omitted, the output is unchanged from before; given, it appends that character's own photo/video counts and its rank among all `HASHTAGS` entries (ties keep `hashtags.json`'s insertion order, no competition-ranking logic). `/抓圖清單`/`/抓圖刪除` share `/抓圖`'s existing "character must be a known hashtags.json key" guard before dispatching — `/抓圖統計` is dispatched before that guard, with its own looser check (`角色` may be empty, but if given must still be a known key), since its option isn't required. `delete_entry` runs both sides through `fix_embed_url()` before comparing — `/抓圖`'s reply shows X/FB posts through their vxtwitter.com/facebed.com embed-proxy link (see below), so pasting that visible link in here has to match the original x.com/facebook.com URL actually stored in `collected.json`.

**`/抓圖`'s optional `作者` filter (`pick_pool` in app.py):** narrows the random-pick pool to entries whose `author` contains the given substring (case-insensitive) before sampling — same matching rule `url_choices` already used for `/抓圖刪除`'s autocomplete, factored out into `pick_pool` so both call sites (and a unit test) share it instead of two near-identical list comprehensions. Empty pool after filtering (either the character has nothing of that type, or nothing from that author) returns a message distinguishing the two cases.

**`/抓圖`'s `角色` is optional too (`pick_random_character` in app.py):** the only command where `角色` isn't required — leave it blank and it first picks a character, then runs through the exact same `pick_pool`/`build_pick_reply` path as if that character had been typed. The character pick is weighted by each candidate's *current* matching-entry count (`random.choices(names, weights=counts)`), not uniform-per-character — weight character A by `len(A's matching pool)` and then sample uniformly within whichever character wins, and the two-stage probability multiplies out to exactly uniform-per-photo across the whole collection (`count_A/total × 1/count_A = 1/total`), without ever materializing a flat list of every character's entries. Recomputed from `load_collected()` on every call, so it tracks new collections automatically — no cached/stored weights to go stale. (An earlier version weighted every candidate character equally regardless of size; changed because that made big collections like `鳴潮` — 6900+ entries — no more likely to surface than a character with one entry, which undersells how much more of the collection they actually are.) Since `/抓圖` is the one command with an optional `角色`, its whole handling had to move above the other commands' shared "character must be a known hashtags.json key" guard (same reason `/抓圖統計` already sits above it) — the old post-guard copy of `/抓圖`'s body was deleted, not left as dead code.

**Entry ordering + `added_at` (`bucket.append(...)` in `/collect`, `build_list_content`/`build_stats_html` in app.py):** each character's list in `collected.json` is append-only, so list order has always *been* chronological (oldest first) — `/抓圖清單` used to slice `shown[:15]` straight off that order, which meant a character with hundreds of entries could only ever show its *oldest* 15, never "what's new". Fixed by reversing before slicing (`list(reversed(shown))[:limit]`), no schema change needed for that part. Separately, every new entry as of this change also gets an explicit `"added_at"` ISO-8601 UTC timestamp (older entries don't have one — nothing backfills it) — the ordering fix didn't strictly need this, but a real timestamp is what a future "what got added this week" query across *all* characters (not just one) would need, since cross-character comparisons can't rely on any single list's position.

**Live ranking page (`GET /stats/html`, `build_stats_html`/`STATS_HTML_TEMPLATE` in app.py):** a bookmarkable, always-current version of the one-off ranking chart — computes the same per-character counts as `build_stats_content` but renders all of them (not just top 10) as a searchable bar list, straight from whatever `load_collected()` returns at request time. Gated by the same `COLLECT_SECRET`, but as a `?key=` query param instead of the `X-Collect-Secret` header every other admin route uses — a header can't be set by just navigating to a bookmarked URL in a browser, so this route deliberately trades the (mild) exposure of a secret sitting in browser history/server access logs for being usable as a plain bookmark. `STATS_HTML_TEMPLATE` is built with `str.replace()` on two `__TOKEN__` placeholders rather than `.format()`/an f-string, since the template's own CSS/JS is full of literal `{`/`}` that would otherwise all need escaping to `{{`/`}}`.

**Backup snapshot (`POST /admin/backup`, `backup_to_github` in app.py):** Upstash's free tier is a single Redis key with no automatic backup — this pushes the current `load_collected()` snapshot to a fixed path (`GITHUB_BACKUP_PATH`, default `collected_backup.json`) in another GitHub repo (`GITHUB_BACKUP_REPO`, via a PAT in `GITHUB_BACKUP_TOKEN`) using the Contents API, overwriting the same path every run rather than date-stamping — the repo's own commit history *is* the point-in-time backup log, no separate retention logic needed. All three env vars are optional; unset, the route returns `{"ok": false, ...}` with a 500 rather than silently no-op-ing, since (unlike `post_announcement`) a failed backup must be visible to whatever's calling it, not swallowed. Gated by the same `X-Collect-Secret` header as `/export`/`/admin/delete`. Nothing in this repo calls it on a schedule — it's meant to be hit periodically by an external cron/uptime service (e.g. cron-job.org) hitting it with that header; set that up separately.

**🗑️ delete button on `/抓圖` replies (`itype == 3` in `interactions()`, `url_hash`/`delete_entry_by_hash` in app.py):** this bot has no persistent Gateway/WebSocket connection, so it can't receive `MESSAGE_REACTION_ADD` events — a reaction-based delete isn't reachable from a pure HTTP-interactions bot. A message **button** is: it fires through the same `/interactions` endpoint as everything else (`type: 3`, `MESSAGE_COMPONENT`). The button's `custom_id` can't safely hold the raw URL (Discord caps it at 100 chars, and FB URLs alone can get close) — it holds `del:{character}:{sha1(url)[:12]}` instead, and the click handler scans that character's bucket for a matching hash. Clicking replies with `type: 7` (`UPDATE_MESSAGE`) so the original message's content changes to a deletion confirmation and its buttons disappear (empty `components`) — which means clicking any one button in a multi-pick message wipes out that whole message's other links too, not just the clicked entry; a known trade-off, not fixed. Button size is fixed by the Discord client — there's no API field to shrink it.

**"Not found" on a delete that actually already worked (Render free-tier wake latency):** confirmed by reproducing against a real `/export` snapshot — `delete_entry`'s matching logic itself is correct, but Render's free tier spins down after idle and the wake-up request can take longer than Discord's 3-second interaction ACK window. When that happens the backend keeps running and *does* complete the delete server-side, but the client-visible response is late/lost, so the user sees what looks like a no-op and retries — the retry's own `delete_entry` call then legitimately finds nothing (the first, silently-successful call already removed it) and reports "找不到". Not a logic bug; both `/抓圖刪除`'s reply and the 🗑️ button's `remove_pick_from_message` comment now say so explicitly rather than leaving it looking like a failure — no other fix attempted (would need Discord's deferred-response pattern, `type: 5` + a followup PATCH, to actually close the 3-second gap, which is a bigger change than this warranted).

**Splitting `/抓圖`'s reply beyond 5 picks (`build_pick_reply`/`send_followups` in app.py):** Discord only auto-generates a preview embed for the first 5 links in one message — picking `數量:6`–`10` would leave the rest as plain unpreviewed links. `build_pick_reply` chunks the numbered lines (and their matching 🗑️ buttons) into groups of 5; the first group is the initial interaction reply, the rest are sent as webhook follow-up messages (`POST /webhooks/{APP_ID}/{interaction_token}`, no 3-second ack deadline) fired from a background thread so they don't block the initial response.

**Data flow:** user likes a post on x.com/instagram.com/facebook.com (in their own logged-in browser, Tampermonkey installed) → `likewatcher.user.js` reads the post's text/URL/media-type off the live page → matches against the character→keyword map served by `GET /hashtags` → `POST /collect` with a shared-secret header → `app.py` **re-validates everything server-side** (URL must match a real post-link regex for one of the three platforms, author is derived from the URL itself where the platform embeds it — X, and Facebook's `/{user}/posts|videos/{id}` shape — rather than trusted from the client, hashtag match is redone server-side) → dedupes by URL → persists into `collected.json`. `/抓圖` only ever reads from that already-built pool.

**Facebook URL support (`FACEBOOK_POST_RE`/`FACEBOOK_REEL_RE`/`FACEBOOK_PHOTO_RE`/`FACEBOOK_GROUP_RE` in app.py):** four URL shapes are recognized — `/{user}/posts|videos/{id}` (author from URL), `/reel/{id}`, `/photo/?fbid={id}`, and `/groups/{group}/posts|permalink/{id}` (author from client, shape-checked, same trust level as Instagram's no-username URLs — group posts don't carry a public username in the URL at all). `permalink.php` and `story.php` are **not** covered — extend with another `elif` branch if you actually need them. The regexes deliberately don't anchor the string end (`$`) since real FB links carry unpredictable tracking query params (`?__cft__[0]=...`) after the part we care about.

**Facebook keyword matching requires `#` — X/IG don't.** `/collect` sets `is_facebook` when any of the four FB regexes matched, and if so requires the keyword to appear as a literal `#keyword` substring (`f"#{t.lower().lstrip('#')}"`, so it works whether or not the keyword is already stored with a leading `#` in `hashtags.json`) instead of the loose "appears anywhere" substring check used for X/IG. This is a deliberate product decision, not a bug: plain-text mentions of a character name are far more common on Facebook (discussion posts, not just fanart) than on X/IG, so the loose match would false-positive constantly. `likewatcher.user.js`'s `matchedCharacters(text, tags, requireHash)` mirrors this client-side (the FB block passes `true`) purely so its pre-submit console log is accurate — the server-side check in `/collect` is what actually enforces it.

**Storage (`load_collected`/`save_collected` in app.py):** Upstash Redis (single key `"collected"`, whole JSON blob) when `UPSTASH_REDIS_REST_URL`/`_TOKEN` are set — required in production because Render's free-tier filesystem is wiped on every redeploy and on spin-down/wake. Falls back to a local `collected.json` file otherwise (local dev only).

**`hashtags.json`:** character → list of keywords, matched as case-insensitive substrings anywhere in the post text (no `#` required by default). A handful of entries are deliberately restricted to `#`-prefixed-only keywords (e.g. `心`, `安可`, `秋水`, `露西`, `蕾貝卡`, `菲比`, `千咲`, and bare `鳴潮` itself) because the bare word is a common word/name that would false-positive-match unrelated posts otherwise. Keep new entries consistent with this pattern — check whether a keyword is generic enough to need the `#`-only treatment before adding it bare. `角色關鍵字對照表.txt` is a human-readable mirror of this file (character：kw1、kw2、... format) — it is **not** auto-generated, update it by hand alongside `hashtags.json`.

**Discord embed rewriting (`fix_embed_url`/`build_link_lines` in app.py):** x.com/twitter.com links are rewritten to `vxtwitter.com` so Discord embeds them inline. Instagram is trickier — `kkinstagram.com` gives Discord's crawler a real media redirect, but a *human* clicking that same link gets bounced to an unrelated third-party site (`kkclip.com`), so IG replies post the `kkinstagram.com` link behind neutral anchor text ("嵌圖用 勿點") plus the real `instagram.com` link on its own line underneath. Facebook links get rewritten to `facebed.com` — confirmed live (curl with a Discordbot user-agent) that Meta specifically blocks Discord's own crawler with a "log in to view" wall on facebook.com directly, even for a public post any browser can see unauthenticated; `facebed.com` gets the real `og:image` through, and 302-redirects a normal browser straight to the real facebook.com URL (no `build_link_lines`-style two-line treatment needed, unlike IG).

**`likewatcher.user.js` — X-only manual-retweet flow, separate from the auto-detect Like path, gated to one device on purpose.** Retweeting a tweet (`[data-testid="retweet"]` then confirming with `[data-testid="retweetConfirm"]` — confirmed live-working; X's confirm menu renders in a portal outside the tweet's own DOM so it can't just be `.closest()`'d, hence `pendingRetweetArticle` tracking which tweet's icon was clicked first) pops a small custom picker UI (`pickCharacters`) instead of scanning the post text for a hashtag match — the post URL/author are taken from `extractTweetLink` directly, no confirmation step (tried prompting for the URL too at first; not needed, the auto-detected link is trusted as-is). The picker hits `GET /autocomplete?q=` (new tiny public route in app.py, just `jsonify(autocomplete_matches(...))`) on every keystroke so it gets the *exact same* homophone/pinyin/bopomofo matching Discord's `/抓圖` autocomplete uses — deliberately not reimplemented in JS. Matches render as a clickable list; picking one turns it into a removable chip and clears the input for the next character, so one retweet can file under several characters at once. Typing a name that exactly matches a known key and hitting Enter also works without a network round trip (fallback for when `/autocomplete` is slow/unreachable). This exists so a post with no hashtag, or one that doesn't match any registered keyword, can still be filed under specific character(s) on purpose. It reuses `/collect` as-is: the submitted `text` is synthesized as each picked character's `#<first keyword>` joined together, which the server's existing hashtag match naturally satisfies in one call — `chars`/`author`/`mediaType` are otherwise handled exactly like the Like path. Since the userscript itself is shared with other people (same `COLLECT_SECRET`, per the Auth model note below), this whole feature is gated behind a **local-only** on/off flag (`GM_getValue("retweetAddEnabled", false)`) toggled via a `GM_registerMenuCommand` — Tampermonkey's local storage is per-browser/per-device and never travels with a script update, so flipping it on in one browser doesn't turn it on for anyone else who has the script installed; it defaults off everywhere.

**`likewatcher.user.js` — Instagram-specific quirks (non-obvious, found via live debugging, don't re-derive from scratch):**
- IG's Reels feed-scroll view renders the caption overlay inside a **closed shadow root** — genuinely unreadable by any DOM query, not a timing issue. Caption and photo/video type are instead read via a same-origin `fetch()` of the post's own canonical URL, parsing the response HTML's `og:description` (caption + hashtags) and `og:url` (contains `/reel/` vs `/p/`, used for media type — a DOM `<video>` query was unreliable and could pick up an unrelated video elsewhere on the page).
- IG post links come in three shapes: `/p/{code}/`, `/reel/{code}/`, and `/reels/{code}/` (plural — the Reels tab's own URL scheme; must not be misparsed as a username "reels"). A generic `/{username}/{code}/` form is also matched as a fallback, with a shortcode-shape heuristic (`looksLikeShortcode`: real codes contain a digit or uppercase letter) plus a reserved-word list to reject non-post nav links like `/legal/privacy/` or `/accounts/meta_verified/`.
- Author extraction relies on the real author's avatar+username links appearing twice in a row pointing at the same href; a single-occurrence link is a commenter or suggested account, not the post's author.

**`likewatcher.user.js` — Facebook block: live-tuned via real reports, still evolving.** Written blind at first (no FB account to test against), then corrected against real Console output the user pasted back — same iterative process that got IG's selectors right, just done after the fact instead of before. Found so far:
- Caption reading does **not** reuse IG's "fetch the post's own URL, read `og:description`" trick — tried that first, but FB's `/photo/?fbid=` viewer URL returns an empty `og:description` (it's not the full wall post, just the photo). FB, unlike IG's Reels, actually renders the caption in plain visible DOM, so `readCaption`/`container.innerText` reads it directly instead (with the same "click 查看更多 to expand truncated text first" trick the X block already uses for its show-original button).
- `findPostLink`/`findPostContainer` prefer a link with a username in it (`/{page}/posts|videos/{id}`) over a nearby `/photo/?fbid=` or `/reel/{id}` link when both exist in reach, since the photo/reel link is often structurally closer to the like button and was getting grabbed first — but plenty of posts (e.g. a page's photo post) genuinely have no `/posts/{id}` link reachable in the DOM at all, so the photo/reel fallback still fires often and is expected, not a bug.
- The like-button selector (`svg[aria-label]` / `[role="button"][aria-label]` matching "讚"/"Like") and the author-extraction heuristic (adjacent duplicate profile links, same trick as IG, plus a `/groups/{g}/user/{id}/` variant for in-group links) are still best-effort guesses. If something's still off, open the Console on a real like click and look for the `[抓圖收藏][FB]` log lines.

**Autocomplete (`autocomplete_matches`/`HASHTAGS_PINYIN`/`HASHTAGS_BOPOMOFO` in app.py):** the 角色 option matches on homophones, not just literal substrings. Every character name is pre-converted to a **toned** pinyin syllable list with `pypinyin.lazy_pinyin(name, style=Style.TONE)` at import time (`HASHTAGS_PINYIN`), and a typed query is converted the same way; a match requires the query's syllables to appear as an exact contiguous run in the target's syllable list (`_contains_syllables`) — not a raw string substring, which would let a short syllable like `jin` false-match as the literal prefix of a longer one like `jing`. Using tone marks also means same-toneless-reading-different-tone pairs (金 jīn vs 瑾 jǐn) don't cross-match. `pypinyin` sometimes guesses the wrong reading for a polyphonic character (e.g. `長離`'s `長` defaulted to `zhǎng` instead of the correct `cháng`) — fix these by registering an override via `load_phrases_dict()` near the top of app.py (one is already there for `長離`); add another line there if a future character's homophone search doesn't work as expected. Separately, `HASHTAGS_BOPOMOFO` (toneless zhuyin per character) covers Discord's autocomplete field sometimes submitting a Zhuyin IME's raw, not-yet-converted bopomofo symbols before a character was ever selected.

**Auth model:** `COLLECT_SECRET` is the only gate on `/collect` — anyone holding it can add entries for any character, with no per-person attribution or revocation (single shared secret, deliberately simple). Since userscript v3.0 the secret is **not** embedded in `likewatcher.user.js` itself — it's stored via `GM_setValue`/`GM_getValue` (prompted once on first use) so the script can safely self-update via Tampermonkey's `@updateURL`/`@downloadURL` without an update clobbering a per-install secret. This is also why the GitHub repo is deliberately public — `@updateURL` points at `raw.githubusercontent.com`, which can't serve from a private repo. No secrets are tracked in git either way (`.env` and `collected.json` are gitignored).

**Auto-announce to Discord channels (`post_announcement` in app.py, `ANNOUNCE_CHANNEL_IDS` — built from the `TEXT_ANNOUNCE_CHANNEL_ID`/`MARUNA_ANNOUNCE_CHANNEL_ID` env vars):** optional — `/collect` calls it when the request both added at least one character *and* carried `"announce": true` in the body. Both env vars are optional and independent; whichever ones are set all get posted to (same content, sent to each — not a routing choice between them), each in its own try/except so one bad channel ID doesn't stop the other from getting the message. The client-side trigger is another local-only `GM_getValue`/`GM_registerMenuCommand` toggle (same pattern as the retweet feature above, default off) baked into `submitCollect` itself, so it covers every collection path (Like on any platform, and the manual retweet-add) from one call site instead of touching each platform block. This needs the bot to actually be a member of the target server with Send Messages in that channel — the **User Install** install path this whole app otherwise relies on does *not* grant that; posting into a channel proactively (as opposed to replying to an interaction) requires a normal bot-scope OAuth invite. Failures (bot not in the server, wrong channel ID, missing permission) are caught and logged (`print(..., flush=True)` — waitress/Render fully buffers stdout otherwise, so unflushed prints can sit invisible in the Logs tab indefinitely even though the code already ran), never allowed to fail `/collect` itself — the actual collection succeeding is what matters, the announcement is a bonus.
